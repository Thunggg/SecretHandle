## 2. Executive Verdict

- **Overall Recommendation:** **2 — Weak Reject** (Calibrated range across reviewers: 2, 2, 3; cannot exceed 3 due to three Critical weaknesses)[cite: 1].
- **Outcome Forecast:** **Advances to Round 2, then Reject (~55% probability)**; Early Reject (~25%); Conditional Accept with heavy shepherding (~18%); outright Accept (~2%)[cite: 1].
- **Top 3 Strengths:** (1) Timely, well-motivated security problem for mobile GUI agents with clear real-world threat articulation (OTP forwarding and Confused Deputy destination redirection)[cite: 2, 3]; (2) Clean capability-based design combining source minting, monotone policy intersection, atomic single-use reservation, and post-entry observation redaction[cite: 4, 5, 6]; (3) Formal transition-system model (Section 5) with clear security reductions mapped directly to attacker goals[cite: 4, 7, 8].
- **Top 3 Critical/Major Problems:** (1) **Critical Prototype-vs-Claim Mismatch & Textual Contradictions:** The paper claims an OS reference monitor in `system_server` (and §4 p. 5 explicitly states an accessibility-service prototype _cannot_ validate reference-monitor assumptions), yet §9.1 admits the prototype is a user-space Accessibility Service + Notification Broker, while §1/§5/Appendix A still describe §7 as "preregistered" and "simulation outputs, not device measurements"[cite: 3, 6, 7, 12, 15, 16]; (2) **Critical Numerical & Methodological Flaws in Section 7:** Table 3 compares end-to-end LLM task time (`48.6 s` for B0) against an in-process Java lookup (`9.30 µs` for B3) in the same `p95 Latency` column, reports an physically impossible `0.13 µs` resolve latency that omits Binder IPC/Keystore/UI injection, and contradicts Algorithm 2 on whether `CALLER_MISMATCH` consumes the handle; (3) **Major Scope Overclaiming:** The Abstract, Intro, and §4 claim handles bind to Credentials, Clipboard, Wallet, and WebView origins, but §3 declares WebView origins out-of-scope (rejected fail-closed) and §7 evaluates _only_ SMS/notification OTPs on a single VLM (Sonnet 4.6) with B2 marked entirely `N/A`[cite: 2, 4, 9, 10].
- **Single Most Important Thing to Fix:** Reconcile the architecture-prototype-evaluation schizophrenia before submission: purge all leftover "preregistered / simulation output" text, honestly frame the implementation as a dual-tier prototype (or move the Vault/Resolver into an actual AOSP system service with real Binder IPC + Keystore MAC measurements), and fix Table 3's apples-to-oranges latency and utility metrics[cite: 3, 6, 10, 12, 15, 16].

## 6. Neutral Summary and Claim-Evidence Table (Phase 3)

### 6.1 Neutral Summary

Mobile GUI agents (such as Mobile-Agent, AutoDroid, and AppAgent) automate tasks by reading screenshots or accessibility trees and synthesizing UI actions[cite: 2, 3]. When a task requires entering sensitive data—such as an SMS one-time password (OTP), login credential, personal identifier, or payment token—exposing the plaintext secret to the agent's visual/accessibility observation allows indirect prompt injections to exfiltrate the value or redirect it into an attacker-controlled application (Confused Deputy attack)[cite: 2, 3]. Even recent placeholder-based anonymization defenses fail under redirection because the agent can instruct the resolver to unmask the placeholder token inside a malicious app[cite: 3, 11]. To solve this, the authors propose **SECRETHANDLE**, an Android OS layer that intercepts secrets at authoritative OS sources (SMS/notification pipelines, Credential Manager, clipboard, wallet) before rendering and mints an unforgeable, cryptographically authenticated opaque handle (`SH-XXXXXX`)[cite: 2, 4, 10]. Each handle is bound to the intersection of a task policy, a source policy, and a type policy specifying the allowed target package, WebView origin, field class, and lifecycle (e.g., single-use with TTL for OTPs)[cite: 5, 6]. The agent sees only the opaque handle and invokes `ENTER(handle, targetNode)`; the OS resolver validates the HMAC authenticator, caller/target identity, and atomic single-use reservation before injecting the secret and masking the destination field from subsequent agent screenshots via an observation redactor[cite: 4, 5, 6]. The authors formalize the state machine with security reductions for confinement, unforgeability, linearizability, and non-disclosure (Section 5)[cite: 7, 8], and evaluate an Android 14 prototype (implemented via an Accessibility Service, Notification Broker, and Vault Resolver) against Mobile-Agent v3.5 (Claude Sonnet 4.6), reporting $0/30$ exposure, $0/30$ redirection, $50/50$ race safety, microsecond vault latency, and zero regression across 10 benign AndroidWorld apps (Section 7)[cite: 9, 10, 12].

1. **[S1 — Problem Formulation & Threat Model for Mobile GUI Agents]** _(Sec. 1, pp. 1–2; Sec. 2, p. 2; Sec. 3, p. 3, Table 1)_: The paper identifies a critical structural flaw in how current mobile GUI agents handle secrets: because agents observe rendered screenshots/accessibility trees and act via UI gestures, any secret that enters the agent's observation channel can be exfiltrated or rerouted by indirect prompt injection[cite: 2, 3]. 2. **[S2 — Clean OS Capability Design & Monotone Policy Intersection]** _(Sec. 4, pp. 3–5, Fig. 1; Sec. 6, p. 8, Alg. 1–2)_: Designing `SECRETHANDLE` around four orthogonal invariants—(1) source minting before rendering, (2) destination predicate intersection $d = D_T \cap D_S \cap \text{TypePolicy}(q, P)$, (3) atomic compare-and-swap reservation with conservative single-use consumption, and (4) pre-registered post-entry observation redaction—is architecturally principled[cite: 5, 6, 9]. 3. **[S3 — Formal Reference-Monitor Model & Security Reductions]** _(Sec. 5, pp. 6–7, Eq. 1–2, Assumptions 5.3–5.8, Thms. 5.9, 5.11, 5.15, Props. 5.12–5.13)_: Unlike many systems papers that make informal security claims, Section 5 explicitly states all six reference-monitor assumptions (Assumptions 5.3–5.8) and proves Destination Confinement (Theorem 5.9), EUF-CMA Handle Unforgeability (Theorem 5.11), Single-Use Linearizability (Proposition 5.12), Expiry Monotonicity (Proposition 5.13), and Agent-View Non-Disclosure (Theorem 5.15)[cite: 7, 8].
4. **[S4 — Clear Demonstration of the Redirection Vulnerability ("Killer Experiment")]** _(Sec. 7, pp. 9–10, Table 3, Qualitative Analysis)_: The comparison between B0 (unprotected), B1 (unbound placeholder), and B3 (`SECRETHANDLE`) under Attack 2 (destination redirection via indirect SMS prompt injection) clearly illustrates why hiding the plaintext string from the LLM is insufficient without OS-level destination confinement at resolution time[cite: 10, 11].

- **Khuyến nghị tổng thể:** **2 — Weak Reject (Từ chối nhẹ)** (Điểm của 3 phản biện giả lập: 2, 2, 3; không thể vượt quá 3 do tồn tại 3 điểm yếu mức Critical)[cite: 1].
- **Dự báo kết quả:** **Vượt qua Vòng 1 nhưng bị Từ chối ở Vòng 2 (~55%)**; Từ chối sớm ở Vòng 1 (~25%); Chấp nhận có điều kiện kèm giám sát (shepherding) gắt gao (~18%); Chấp nhận thẳng (~2%)[cite: 1].
- **3 Điểm mạnh lớn nhất:** (1) Bài toán bảo mật cho tác nhân giao diện di động (Mobile GUI Agents) rất thời sự, mô tả rõ kịch bản lộ mã OTP và tấn công chuyển hướng đích (Confused Deputy destination redirection)[cite: 2, 3]; (2) Kiến trúc dựa trên capability handle sạch sẽ, kết hợp khởi tạo tại nguồn, giao (intersection) chính sách đơn điệu, khóa giữ chỗ nguyên tử một lần (atomic CAS reservation) và che khuất màn hình sau khi điền[cite: 4, 5, 6]; (3) Mô hình hình thức hóa ở Mục 5 chặt chẽ, nêu rõ các giả định và chứng minh bảo mật khớp với mục tiêu tấn công[cite: 4, 7, 8].
- **3 Vấn đề Nghiêm trọng (Critical/Major) lớn nhất:** (1) **Mâu thuẫn nghiêm trọng giữa kiến trúc tuyên bố, nguyên mẫu thực thi và văn bản sót lại (W1):** Bài báo tuyên bố xây dựng reference monitor trong `system_server` (và Mục 4 trang 5 tự khẳng định nguyên mẫu Accessibility Service ở user-space _không thể_ xác thực giả định reference monitor), nhưng Mục 9.1 lại thừa nhận nguyên mẫu thực nghiệm chính là một Accessibility Service + Notification Broker dùng `TYPE_ACCESSIBILITY_OVERLAY`, trong khi Mục 1, Mục 5 và Phụ lục A vẫn viết rằng Mục 7 là "kế hoạch đánh giá đăng ký trước (preregistered)" và "kết quả mô phỏng (simulation outputs), không phải đo đạc trên thiết bị"[cite: 3, 6, 7, 12, 15, 16]; (2) **Lỗi số liệu và phương pháp luận nghiêm trọng ở Mục 7 (W2):** Bảng 3 xếp chung thời gian suy luận toàn trình của LLM (`48.6 s` của B0) với thời gian tra cứu bộ nhớ trong tiến trình Java (`9.30 µs` của B3) vào cùng một cột `p95 Latency`, báo cáo độ trễ giải mã `0.13 µs` (130 nano-giây) bất khả thi về mặt vật lý nếu tính cả Binder IPC/Keystore/điền UI, và tự mâu thuẫn với Thuật toán 2 về việc lỗi `CALLER_MISMATCH` có hủy luôn mã OTP hay không[cite: 9, 10, 11]; (3) **Tuyên bố quá mức phạm vi thực nghiệm (W4, W5):** Tóm tắt và Mục 4 tuyên bố hỗ trợ Credential Manager, Clipboard, Wallet và gắn kết nguồn WebView (WebView origin binding), nhưng Mục 3 lại xếp WebView ra ngoài phạm vi (từ chối fail-closed) và Mục 7 chỉ đánh giá duy nhất mã OTP qua SMS trên 1 mô hình VLM (Claude Sonnet 4.6) đồng thời để trống `N/A` toàn bộ hàng B2 trong Bảng 3[cite: 2, 4, 9, 10].
- **Việc quan trọng nhất phải sửa ngay:** Thống nhất hoàn toàn giữa kiến trúc, nguyên mẫu và thực nghiệm trước khi nộp: xóa bỏ mọi câu chữ sót lại về "preregistered / simulation outputs", trình bày trung thực kiến trúc nguyên mẫu trên Android 14 (hoặc đo đạc đầy đủ độ trễ Binder IPC + Keystore MAC + điền UI thực tế), và sửa lại Bảng 3 để tách biệt độ trễ suy luận LLM với độ trễ bảo mật cũng như tách biệt độ hữu dụng (Utility $U$) khi không có tấn công và khi bị tấn công[cite: 3, 6, 10, 12, 15, 16].
